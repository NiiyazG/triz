# Примеры

> Примеры иллюстративные. Фактические параметры, эффекты и метрики нужно проверять в конкретном проекте.

## Пример 1. Ускорить загрузку страницы без потери качества изображений

### Проблема
Сайт выглядит хорошо, но грузится медленно из-за тяжёлых изображений.

### ТП
Если сильнее сжимать изображения, страница открывается быстрее, но картинка становится хуже.

### ФП
Изображение должно быть маленьким для передачи и большим по качеству для просмотра.

### ИКР
Пользователь сразу видит страницу в хорошем восприятии, а полное качество приходит без заметного ожидания.

### Приёмы
- **26 Копирование**: превью вместо оригинала на первом шаге
- **15 Динамичность**: разные версии под сеть и экран
- **28 Замена механической схемы**: WebP/AVIF вместо старых форматов
- **10 Предварительное действие**: подготовить все размеры на build-этапе

### Решение
Blur-preview + `srcset` + lazy loading + современные форматы.

## Пример 2. Сделать чашку кофе горячей дольше, не обжигая руки

### Проблема
Кофе должен дольше сохранять тепло, но внешняя поверхность кружки не должна становиться слишком горячей.

### ТП
Если повысить теплоизоляцию, напиток дольше горячий, но кружка становится массивнее и дороже.

### ФП
Стенка кружки должна хорошо держать тепло внутри и плохо передавать тепло наружу.

### ИКР
Кружка сама удерживает температуру напитка, оставаясь удобной и безопасной для руки.

### Приёмы
- **30 Гибкие оболочки и тонкие плёнки**: теплоизолирующее покрытие
- **31 Пористые материалы**: воздушные поры как изолятор
- **40 Композиционные материалы**: разные слои под внутреннюю и внешнюю задачи
- **3 Местное качество**: внутренняя и внешняя поверхности имеют разные свойства

### Решение
Двустенная кружка с воздушным зазором и наружной поверхностью из материала с низкой теплопроводностью.

## Пример 3. Уменьшить очереди в техподдержке, не нанимая новых людей

### Проблема
Запросов много, время ожидания растёт, но расширять команду нельзя.

### ТП
Если обрабатывать больше запросов вручную, качество ответов падает и команда выгорает.

### ФП
Поддержка должна отвечать быстро и при этом сохранять точность и персонализацию.

### ИКР
Система сама снимает типовые запросы, а люди тратят время только на сложные случаи.

### Приёмы
- **6 Универсальность**: единый портал с FAQ, статусами и заявками
- **25 Самообслуживание**: дать пользователю самому решить типовые сценарии
- **23 Обратная связь**: маршрутизация по категориям и результатам решений
- **2 Вынесение**: отделить типовые обращения от сложных

### Решение
Запустить self-service help center, автоклассификацию тикетов и шаблоны ответов с эскалацией только сложных случаев.

## Пример 4. API Gateway: latency vs reliability под нагрузкой

### Проблема
API Gateway обрабатывает 10K RPS, но при пиковых нагрузках (Чёрная пятница) latency вырастает с 50ms до 3s, часть запросов падает с 502.

### ТП
Если добавить больше проверок (аутентификация, ratelimiting, валидация), система безопаснее, но время ответа растёт и throughput падает.

### ФП
Gateway должен пропускать запросы мгновенно для скорости и проверять каждый запрос для безопасности.

### ИКР
Gateway сам обеспечивает безопасность без добавления задержки в критический путь — вредные запросы отсекаются, полезные проходят без торможения.

### Приёмы
- **1 Дробление**: разделить Gateway на data plane (fast path, только роутинг) и control plane (проверки, политики)
- **10 Предварительное действие**: кэшировать результаты аутентификации (JWT validation) и ratelimiting-счётчики в Redis
- **15 Динамичность**: адаптивно отключать некритичные проверки (детальное логирование, необязательные заголовки) при превышении latency SLO
- **26 Копирование**: развернуть несколько инстансов Gateway за load balancer, держать горячий кэш сессий на каждом

### Решение
Envoy/Kong с разделением на data plane (минимальный latency) и control plane (асинхронные проверки), Redis для кэша токенов, адаптивное отключение нестрогой валидации при p95 > 100ms.

## Пример 5. Кэш: свежесть данных vs скорость ответа

### Проблема
REST API кэширует ответы в Redis (TTL 5 мин). Бизнес жалуется: изменения в БД не видны пользователям до истечения TTL.

### ТП
Если уменьшить TTL кэша, данные актуальнее, но нагрузка на БД растёт и latency увеличивается.

### ФП
Кэш должен быстро отдавать данные и при этом мгновенно отражать изменения в БД.

### ИКР
Система сама знает, когда данные изменились, и обновляет кэш только для изменившихся записей — пользователь всегда видит актуальные данные без деградации скорости.

### Приёмы
- **15 Динамичность**: разный TTL для разных типов данных (конфиги — час, цены — минута, inventory — инвалидация по событию)
- **23 Обратная связь**: инвалидация кэша через CDC (Change Data Capture) — БД отправляет событие изменения → cache warmer обновляет только затронутые записи
- **19 Периодическое действие**: вместо сплошного кэширования — фоновая job раз в 30 секунд прогревает кэш для hot-записей
- **10 Предварительное действие**: cache stampede protection — за 10 секунд до истечения TTL фоновый процесс обновляет запись, а не ждёт промаха

### Решение
Redis + CDC через Debezium/Kafka: при изменении в БД событие попадает в cache-invalidation service, который точечно сбрасывает/обновляет затронутые ключи. Lazy + eager кэширование с разными TTL по типам данных.

## Пример 6. Микросервисы: модульность vs наблюдаемость

### Проблема
Система из 12 микросервисов. Когда заказ падает с ошибкой, невозможно отследить сквозной запрос через все сервисы — каждый логирует в свой stdout, формат разный.

### ТП
Если унифицировать логирование и трейсинг, система наблюдаема, но каждый сервис усложняется (добавляется tracing SDK, стандартизация форматов).

### ФП
Сервисы должны быть простыми и независимыми для скорости разработки, и одновременно связанными общей системой наблюдаемости для отладки.

### ИКР
Система сама предоставляет сквозную картину запроса без того, чтобы каждый разработчик вручную настраивал трейсинг в своём сервисе.

### Приёмы
- **5 Объединение**: единый стандарт логирования (структурированный JSON) и трейсинга (OpenTelemetry) как shared-библиотека, подключаемая одной строкой
- **24 Посредник**: sidecar-контейнер (Envoy/Linkerd) автоматически добавляет tracing-заголовки ко всем HTTP/gRPC вызовам — сервисы не знают о трейсинге
- **23 Обратная связь**: Jaeger/Grafana Tempo собирает спаны со всех сервисов, дашборд показывает сквозной запрос с таймингами каждого hop
- **28 Замена механической схемы**: заменить grep по логам на структурированный поиск в Loki/ElasticSearch с correlation ID

### Решение
Service mesh (Istio/Linkerd) + OpenTelemetry SDK как shared library + Jaeger для трейсинга + Loki для агрегации логов. Correlation ID передаётся через заголовки автоматически, разработчикам не нужно думать о трейсинге — он работает из коробки.
