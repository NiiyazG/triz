# Axiomatic Design — детекция связанных требований

> Статус: **canonical**. Источник: Nam P. Suh. Первоисточник: https://en.wikipedia.org/wiki/Axiomatic_design

Axiomatic Design (AD) оценивает качество конструкции по двум аксиомам: независимость функциональных требований и минимум информационного содержания. Полезен как мост к ТРИЗ: **связанная (coupled) конструкция — это техническое противоречие**, а развязка требований — способ его снятия.

## Две аксиомы

1. **Axiom 1 — независимость:** функциональные требования (FR) должны оставаться независимыми; изменение одного DP (design parameter) не должно нарушать другие FR.
2. **Axiom 2 — информация:** минимизируй информационное содержание (вероятность удовлетворения требований); проще — меньше информации.

## Типы конструкций по матрице проектирования

| Тип | Матрица | Следствие |
|---|---|---|
| Uncoupled | диагональная | каждый DP влияет на один FR — идеал |
| Decoupled | треугольная | порядок DP решает; последовательная настройка |
| Coupled | полная | DP влияют на несколько FR — требуется итерация/компромисс |

## Процедура

1. Перечисли **FR** (чего требует система) на верхнем уровне.
2. Сопоставь каждому FR **DP** (чем это реализуется).
3. Построй матрицу FR×DP, отметь влияния.
4. Определи тип (uncoupled/decoupled/coupled).
5. Если coupled — сформулируй техническое противоречие: «улучшение FR1 через DP1 ухудшает FR2» и примени ТРИЗ (разделение, принципы, Su-Field).
6. Иерархически разложи (зигзаг: FR → DP → FR под-уровня → …).

## Связь с ТРИЗ

Coupled-конструкция → ТП → изобретательские принципы/разделение. Axiom 2 → критерий «идеальность»: меньше информации = проще и надёжнее.

## Ограничения применимости

- Аксиомы — ориентиры, а не теоремы; на практике допустима «приемлемо decoupled» конструкция.
- Не даёт способа генерации самих DP — комбинируй с ТРИЗ/SIT/C-K.

## Проверка

- [ ] FR и DP разделены (требование vs средство);
- [ ] тип матрицы определён;
- [ ] coupled-связь переведена в противоречие и снята;
- [ ] развязка не создала новую связь.
