# Software-противоречия

> Это авторская доменная адаптация, а не официальная матрица Альтшуллера.

## Как пользоваться

1. Найди свой конфликт в таблице ниже
2. Возьми 3-4 рекомендованных приёма
3. Для каждого ответь: как именно этот приём снимает конфликт в конкретном случае
4. Проверь через ИКР: система сама устраняет конфликт без новых проблем?

## Антипаттерны: когда ТРИЗ в софте вредит

| Приём | Как НЕ надо | Правильно |
|---|---|---|
| 1 Дробление | Дробить монолит на 50 наносервисов «на всякий случай» | Начинать с 3-5 сервисов по доменам, дробить по мере роста боли |
| 5 Объединение | Запихивать всё в монорепо без инструментов | Монорепо имеет смысл только с shared configs, affected-детекцией в CI |
| 6 Универсальность | «Универсальный фреймворк» который решает все проблемы и не решает ни одной | Делать универсальным только то, что реально переиспользуется в ≥3 местах |
| 10 Предварительное действие | Кэшировать всё подряд, потом cache invalidation — главная проблема | Кэшировать только read-heavy данные, явно определить TTL и стратегию инвалидации |
| 23 Обратная связь | Алерты на всё → alert fatigue → люди игнорируют реальные инциденты | Только actionable алерты, SLO-based подход, эскалация по severity |
| 26 Копирование | Создавать копию БД для каждого микросервиса → data inconsistency hell | Разделять на read-реплики (одна source of truth) и CQRS для сложных случаев |
