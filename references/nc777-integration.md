# Опциональная интеграция NC777

> Этот файл описывает композицию с отдельно установленным навыком `nc777-prompts`. Интеграция опциональна; отсутствие внешнего навыка не должно ломать TRIZ workflow.

Как использовать 9 ролей NC777 в конвейере TRIZ-решения. Для каждой роли: зона ответственности в TRIZ-конвейере, входной/выходной артефакт, промпт-шаблон и пример.

---

## 1. Prophet + TRIZ (диагностика)

**Берёт на себя**: формулировка противоречия (ТП + ФП), сбор контекста, выбор трека сложности.

| Поле | Значение |
|---|---|
| Вход | Сырая проблема от пользователя |
| Выход | Risk Map с явно сформулированным ТП и ФП + выбранный трек |
| Критерий done | ТП и ФП сформулированы, трек выбран, ресурсы системы перечислены |

### Промпт-шаблон

```
Проведи TRIZ-диагностику:
- Проблема: [описание]
- Что уже пробовали: [если известно]
- Ограничения: [нельзя трогать X, бюджет Y]

На выходе:
1. ТП (техническое противоречие): «если улучшить A, ухудшается B»
2. ФП (физическое противоречие): «элемент должен быть X и не-X»
3. Доступные ресурсы системы (технологии, данные, время, люди)
4. Рекомендованный трек: быстрый / стандартный / полный
5. Risk Map: 3 вероятные точки отказа при попытке решения
```

### Пример: «Кэш устаревает, пользователи видят старые цены»

**Вывод Prophet:**

```
ТП: Если уменьшить TTL кэша, данные актуальнее, но нагрузка на БД растёт (latency ×3)
ФП: Кэш должен мгновенно отражать изменения БД и при этом не нагружать БД лишними запросами
Ресурсы: Redis (TTL=5мин), PostgreSQL, Kafka (уже в стеке), Debezium (уже настроен)
Трек: Быстрый — конфликт простой, ресурсы богатые
Risk Map:
  1. Cache invalidation storm при массовом обновлении (лавина запросов к БД)
  2. При CDC-подходе — задержка events из Debezium (100-500ms окно несогласованности)
  3. Ручное управление TTL для разных типов данных — пропустят новый тип
```

## 2. Architect + TRIZ (план)

**Берёт на себя**: выбор 3-5 приёмов из 40, построение ИКР, веполь (если нужно), план реализации.

| Поле | Значение |
|---|---|
| Вход | Risk Map от Prophet, Software Decision Table |
| Выход | TRIZ-план: выбранные приёмы, ИКР, веполь, шаги реализации с технологиями |
| Критерий done | Приёмы выбраны не случайно, каждый объяснён применительно к задаче |

### Промпт-шаблон

```
Построй TRIZ-архитектуру решения на основе:
- ТП: [противоречие]
- ФП: [физическое противоречие]
- Ресурсы: [список]
- Трек: [быстрый/стандартный/полный]

Выполни:
1. ИКР: «система сама [полезное действие], не усложняясь»
2. Из Software Decision Table и таблицы противоречий выбери 3-5 приёмов
3. Для каждого приёма: как именно он снимает конфликт? (конкретно, с кодом/архитектурой)
4. Если конфликт связан с взаимодействием объектов → вепольная модель
5. План: шаги с указанием технологий (Redis, Kafka, K8s...)
```

### Пример: «Кэш устаревает»

**Вывод Architect:**

```
ИКР: Система сама инвалидирует кэш точечно при изменении данных,
     пользователь всегда видит актуальные цены без дополнительной нагрузки на БД.

Приёмы:
  15 Динамичность → разные TTL: цены 30s, описания 24h, inventory — инвалидация по событию
  23 Обратная связь → CDC (Debezium) ловит изменения в БД → Kafka → cache-invalidator → Redis DEL
  19 Периодическое действие → фоновая прогревка кэша для top-1000 товаров каждые 30s
  10 Предварительное действие → cache stampede protection: обновление записи за 10s до TTL

Веполь:
  В1: пользовательский запрос
  В2: кэшированные данные в Redis
  П: механизм инвалидации
  Конфликт: поле (инвалидация) работает по времени, а не по событиям
  Преобразование: заменить временно́е поле на событийное (CDC)

План:
  1. Настроить Debezium connector на таблицы с ценами и inventory
  2. Cache-invalidator service: слушает Kafka-топик → Redis DEL для затронутых ключей
  3. Redis: настроить TTL 30s для цен, 24h для описаний
  4. Cache warmer: cron каждые 30s → подгружает top-1000 товаров
  5. API: добавить stampede protection (SET NX с коротким TTL)
```

## 3. Reviewer + TRIZ (критический взгляд на план)

**Берёт на себя**: фальсификация TRIZ-решения — не создаёт ли решение новое противоречие?

| Поле | Значение |
|---|---|
| Вход | TRIZ-план от Architect |
| Выход | Review Report: вердикт + найденные скрытые противоречия |
| Критерий done | Проверены все приёмы на побочные эффекты |

### Промпт-шаблон

```
Проверь TRIZ-решение на скрытые противоречия:
- Исходное ТП: [противоречие]
- Предложенные приёмы: [список с обоснованием]
- План реализации: [шаги]

Ответь:
1. Снимает ли каждый приём заявленное противоречие, или просто переносит вред?
2. Какие НОВЫЕ противоречия создаёт каждый приём?
3. Есть ли приёмы, которые противоречат друг другу?
4. Не пропущен ли очевидный приём, который лучше подходит?
5. Вердикт: APPROVED / NEEDS CHANGES
```

### Пример: «Кэш устаревает»

**Вывод Reviewer:**

```
VERDICT: APPROVED with warnings

1. Приёмы снимают заявленное противоречие:
   - 15 Динамичность ✓ — разные TTL реально снижают нагрузку без потери актуальности
   - 23 Обратная связь ✓ — CDC решает корневую причину (временна́я, а не событийная инвалидация)
   - 19 Периодическое ✓ — фоновая прогревка сглаживает cold-start
   - 10 Предварительное ✓ — stampede protection предотвращает лавину

2. Новые противоречия:
   - CDC добавляет latency окно 100-500ms (eventual consistency, не strong)
     → не фатально для цен, критично для inventory (остаток на складе)
     → РЕКОМЕНДАЦИЯ: для inventory использовать синхронную инвалидацию (write-through)
   - Cache warmer создаёт постоянную фоновую нагрузку на БД
     → OK пока товаров top-1000; при росте до 100K — нужен сэмплинг

3. Конфликт между приёмами: нет

4. Пропущенный приём: 26 Копирование — read-реплика БД для cache warmer,
   чтобы он не нагружал primary. Рекомендую добавить.

5. VERDICT: APPROVED, добавить рекомендации в план.
```

## 4. Developer + TRIZ (реализация)

**Берёт на себя**: превращает TRIZ-приёмы в конкретный код / конфигурацию. **ВСЕ задачи ПО — через Codex CLI.**

| Поле | Значение |
|---|---|
| Вход | TRIZ-план + Review Report |
| Выход | Работающий код + тесты |
| Критерий done | Приёмы реализованы, тесты проходят, post-Codex пайплайн выполнен |

### Промпт-шаблон для Codex

```
Реализуй TRIZ-решение. Контекст:

Исходная проблема: кэш Redis (TTL 5мин) устаревает.
TRIZ-приёмы к реализации:
  - 15 Динамичность: разные TTL для разных типов ключей
    → цены: 30s, описания: 24h, inventory: инвалидация по событию
  - 23 Обратная связь: CDC через Debezium → Kafka → cache-invalidator
  - 19 Периодическое: cache warmer cron каждые 30s для top-1000
  - 10 Предварительное: cache stampede protection (SET NX lock за 10s до TTL)

Стек: Redis, PostgreSQL, Kafka, Debezium
Файлы: cache-config.yaml, cache-invalidator.js, cache-warmer.js

План:
1. cache-config.yaml: маппинг ключ → TTL / стратегия инвалидации
2. cache-invalidator.js: consumer Kafka → Redis DEL
3. cache-warmer.js: cron → SELECT top-1000 → Redis SET

После реализации: проверь синтаксис, напиши тесты.
```

## 5. Documenter + TRIZ (фиксация)

**Берёт на себя**: документирует TRIZ-решение — какое противоречие, какие приёмы, почему сработало.

| Поле | Значение |
|---|---|
| Вход | Результат реализации |
| Выход | TRIZ Decision Record + commit message |

### Промпт-шаблон

```
Задокументируй TRIZ-решение:
- Исходное противоречие: [ТП + ФП]
- Применённые приёмы: [нумерация и обоснование]
- Что изменилось: [метрики до/после]
- Почему сработало: [какой именно аспект приёма снял конфликт]
- Могло ли быть лучше: [альтернативные приёмы, которые рассматривались]
```

## 6. QA + TRIZ (верификация)

**Берёт на себя**: проверяет, что противоречие ДЕЙСТВИТЕЛЬНО снято, а не замаскировано.

| Поле | Значение |
|---|---|
| Вход | Реализованное решение |
| Выход | QA Report: метрики до/после, проверка на регрессии |
| Критерий done | Противоречие снято по measurable критериям |

### Промпт-шаблон

```
Проверь TRIZ-решение. Исходное противоречие: [ТП]

Проверочные сценарии:
1. Нормальный режим: [метрика до] → [метрика после]
2. Пиковая нагрузка: проверяем, не вернулось ли противоречие
3. Edge cases: [null, empty, double-click, race condition]
4. Регрессии: смежные системы не пострадали?

Если FAIL → передай Pitbull.
```

### Пример: «Кэш устаревает»

```
QA Report: PASS ✓

1. Актуальность цен: было — до 5 мин устаревания, стало — <500ms (CDC latency)
2. Нагрузка на БД: было — 5000 rps, стало — 4800 rps (cache warmer добавил ~30 rps, ок)
3. Stampede test: при истечении TTL для 1000 ключей одновременно — 0 промахов (SET NX отработал)
4. Регрессии: API latency p95 стабилен (45ms → 42ms), ошибок нет
```

## 7. Saboteur + TRIZ (взлом решения)

**Берёт на себя**: намеренно ломает TRIZ-решение — «а что если приём применён неправильно?»

| Поле | Значение |
|---|---|
| Вход | Работающее решение после QA |
| Выход | Sabotage Report: где приём создал новую проблему |
| Критерий done | Все edge-cases пройдены |

### Промпт-шаблон

```
Попробуй сломать TRIZ-решение. Применены приёмы: [список].

Для каждого приёма проверь:
1. Что если применить его СЛИШКОМ сильно? (over-application)
2. Что если применить его НЕ полностью? (under-application)
3. Что если условия изменились? (приём работал, а теперь вредит)

Edge cases: null/undefined, 10000 запросов/сек, отключение внешнего сервиса.
```

### Пример: «Кэш устаревает»

```
Sabotage Report:

1. 15 Динамичность — over-application:
   Что если TTL=1s для всех ключей? → Redis становится бесполезен, БД под лавиной.
   Что если забыли новый тип данных (flash_sale) — он получает default TTL 5м и устаревает.
   ➤ Рекомендация: default TTL должен быть консервативным (5м), исключения — осознанными.

2. 23 Обратная связь — under-application:
   Что если Kafka lag растёт? → CDC-события задерживаются, кэш устаревает.
   ➤ Рекомендация: мониторить consumer lag, алертить при >1s.

3. 19 Периодическое — условие изменилось:
   Что если товаров стало 100K (не 1K)? → cache warmer создаёт значимую нагрузку.
   ➤ Рекомендация: сэмплирование или динамический top-N по частоте запросов.
```

## 8. Pitbull + TRIZ (восстановление)

**Берёт на себя**: если TRIZ-решение не сняло противоречие — ищет root cause и правит.

| Поле | Значение |
|---|---|
| Вход | FAIL-отчёт от QA или Saboteur |
| Выход | Pitbull Attempt Log — 3 попытки с разными подходами |
| Критерий done | Противоречие снято ИЛИ честный рапорт с гипотезами |

### Промпт-шаблон

```
TRIZ-решение провалилось. Исходное ТП: [противоречие]
Применены приёмы: [список], но [метрика] не улучшилась.

3 попытки:
Attempt 1: проверить, правильно ли интерпретирован приём. Может, software-паттерн выбран не тот?
Attempt 2: заменить 1-2 приёма на альтернативные из таблицы противоречий.
Attempt 3: вернуться к ФП — может, противоречие сформулировано неверно?

Каждая попытка — новый подход, не вариация предыдущего.
```

## 9. Cleaner + TRIZ (порядок после решения)

**Берёт на себя**: удаляет временные файлы, финализирует документацию TRIZ-решения.

| Поле | Значение |
|---|---|
| Вход | Финальное состояние после решения |
| Выход | Cleaner Summary: что удалено + обновлённая документация |
| Критерий done | Worktree чистый, TRIZ Decision Record записан |

---

## Полный конвейер NC777+TRIZ (шпаргалка)

```
Пользователь → Prophet (ТП/ФП, трек)
           → Architect (приёмы, ИКР, веполь, план)
           → Reviewer (фальсификация: скрытые противоречия?)
           → Developer/Codex (реализация)
           → QA (метрики до/после)
           → Saboteur (edge cases, over-application)
           → Pitbull (если FAIL)
           → Cleaner (документация, очистка)
```

### Правила выбора ролей по сложности TRIZ-задачи

| Сложность | Минимальный набор ролей |
|---|---|
| Простой конфликт (быстрый трек) | Prophet → Architect → Developer → QA |
| Средний конфликт (стандартный трек) | Prophet → Architect → Reviewer → Developer → QA → Saboteur → Cleaner |
| Сложный конфликт (полный трек) | Все 9 ролей: Prophet → Architect → Reviewer(×2) → Developer → QA → Saboteur → Pitbull → Cleaner |
