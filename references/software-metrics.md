# Метрики software-решений

> Все численные значения в примерах являются синтетическими. Порог, длительность и размер выборки должны определяться данными и риском конкретного проекта. См. `evaluation.md`.

Как количественно проверить, что TRIZ-приёмы действительно сняли противоречие, а не замаскировали его.

## Таблица метрик по типам конфликтов

| Тип конфликта | Метрика «до» | Метрика «после» | Как измерить | Целевой порог |
|---|---|---|---|---|
| **Latency vs Throughput** | p95 latency при N RPS | p95 latency при том же N RPS | Prometheus histogram + Grafana | p95 < 2× baseline |
| **Latency vs Consistency** | Stale data window (max lag) | Stale data window после решения | CDC metrics, Kafka consumer lag | <100ms для цен, <5s для конфигов |
| **Scalability vs Simplicity** | Бизнес-метрика: time-to-deploy новой фичи | Time-to-deploy после решения | CI/CD дашборд (DORA metrics) | <1 дня (было >3) |
| **Security vs UX** | Время аутентификации (p50) | Время аутентификации + satisfaction score | APM traces + NPS опрос | p50 < 500ms, NPS > 0 |
| **Deploy speed vs Stability** | Change failure rate | Change failure rate после canary/feature flags | DORA metrics | <5% (было >15%) |
| **Dev velocity vs Code quality** | Багов в проде / неделя | Багов в проде / неделя после модуляризации | Sentry/Bugsnag | Снижение на 50%+ |
| **Cache hit rate vs Freshness** | Cache hit rate + stale read count | Новые значения обеих метрик | Redis INFO + application-level counters | Hit rate >80%, stale reads → 0 |
| **Microservices vs Debuggability** | Mean Time To Detect (MTTD) | MTTD после unified observability | PagerDuty/Incident management | MTTD < 5 мин (было >30) |
| **Throughput vs Cost** | RPS per $ cloud spend | RPS per $ после оптимизации | Cloud billing + RPS дашборд | Улучшение на 30%+ |
| **Modularity vs Performance** | Service mesh overhead (p99 added latency) | Overhead после оптимизации | Istio/Envoy metrics | <5ms added (было >20ms) |
| **Flexibility vs Complexity** | Cyclomatic complexity + feature velocity | Обе метрики после plugin-архитектуры | SonarQube + Jira velocity | Complexity ↓30%, velocity ↑ |
| **Availability vs Cost** | Uptime % + monthly infra bill | Обе метрики после решения | CloudWatch + billing | Uptime ≥99.9%, cost ≤ baseline |

## Как провести A/B-тест TRIZ-решения

### Шаг 1: Измерь baseline (3-7 дней)

Собери метрики ДО применения TRIZ-приёмов. Минимальный набор:
- Бизнес-метрика (latency, error rate, conversion)
- Техническая метрика (CPU, memory, DB load)
- Пользовательская метрика (NPS, satisfaction, bounce rate)

### Шаг 2: Сформулируй гипотезу

```
Гипотеза: применение приёмов [N1, N2, N3] снизит [ухудшаемый параметр]
с X до Y без ухудшения [улучшаемый параметр] более чем на Z%.
```

Пример:
```
Гипотеза: применение 23 (CDC-инвалидация) и 15 (разные TTL) снизит
stale data window с 5 мин до <500ms без падения cache hit rate ниже 80%.
```

### Шаг 3: Разверни решение

- **Canary deploy**: 5% → 25% → 100% трафика с мониторингом метрик на каждом шаге
- **Feature flag**: включить TRIZ-решение для 10% пользователей, сравнить с контрольной группой
- **Shadow mode**: пустить новый код в параллель со старым, сравнивать результаты

### Шаг 4: Собирай метрики (минимум 24 часа)

На каждом шаге canary проверяй:
- Основная метрика улучшилась?
- Побочные метрики не ухудшились?
- Новое противоречие не появилось?

### Шаг 5: Прими решение

| Результат | Действие |
|---|---|
| Метрики улучшились, побочных нет | ✅ Полный rollout |
| Метрики улучшились, но появилась побочная | ⚠️ Saboteur — найти и устранить новое противоречие |
| Метрики не изменились | 🔄 Pitbull — переформулировать противоречие, выбрать другие приёмы |
| Метрики ухудшились | ❌ Rollback + анализ: почему TRIZ-приём не сработал? |

## Пример: A/B-тест cache invalidation

### Baseline (неделя до)
```
Cache hit rate: 92%
Stale data window: 5 мин (TTL)
p95 latency: 45ms
DB load: 5000 rps
```

### Гипотеза
```
Применение 23 (CDC) + 15 (разные TTL) снизит stale window
до <500ms без падения hit rate ниже 80%.
```

### Canary (5% → 100%)
| Трафик | Hit rate | Stale window | p95 latency | DB load |
|---|---|---|---|---|
| 0% (baseline) | 92% | 300s | 45ms | 5000 rps |
| 5% (canary) | 89% | 0.3s | 42ms | 4950 rps |
| 25% | 88% | 0.4s | 43ms | 4980 rps |
| 100% | 87% | 0.35s | 42ms | 4800 rps |

### Вывод
- ✅ Stale window: 5 мин → 350ms (улучшение в 850 раз)
- ✅ Hit rate: 92% → 87% (в пределах гипотезы, >80%)
- ✅ DB load: снизилась (CDC разгрузил повторные запросы)
- ✅ p95 latency: стабильна (42-45ms)
- ⚠️ Новое противоречие: CDC добавляет 100-500ms latency на propagation. Для inventory (остатки) критично → добавили синхронную инвалидацию (write-through)

**Решение**: ✅ Полный rollout.

## Когда TRIZ-решение НЕ сработало

Если метрики не улучшились — проверь эти 5 причин:

| # | Причина | Диагностика | Исправление |
|---|---|---|---|
| 1 | Неверно сформулировано противоречие | Метрики не изменились ни по одному параметру | Вернуться к Prophet, переформулировать ТП/ФП |
| 2 | Приём интерпретирован неправильно | Техническая реализация не соответствует сути приёма | Свериться с `software-techniques.md`, подобрать другой software-паттерн |
| 3 | Новое противоречие перевесило пользу | Одна метрика улучшилась, другая резко упала | Saboteur — найти новое противоречие, применить к нему TRIZ |
| 4 | Недостаточно ресурсов системы | Решение требует инфраструктуры, которой нет | Переформулировать ИКР: решение ТОЛЬКО из доступных ресурсов |
| 5 | Задача не TRIZ-овская | Конфликта нет — это просто нехватка ресурсов или баг | Не применять TRIZ. Решать как обычную инженерную задачу. |

## Пирамида метрик TRIZ

```
        ┌──────────────┐
        │  Бизнес-эффект │  ← «стало лучше для пользователя?»
        ├──────────────┤
        │   Противоречие  │  ← «ключевая метрика снятия конфликта»
        ├──────────────┤
        │  Побочные       │  ← «не появилось ли новое противоречие?»
        ├──────────────┤
        │  Технические    │  ← «CPU, memory, latency — базовое здоровье»
        └──────────────┘
```

Измеряй все 4 уровня. Если улучшился только технический, а бизнес-эффекта нет — решение не сняло противоречие, а просто оптимизировало систему.
