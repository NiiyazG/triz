# 40 приёмов: software-адаптации

> Статус соответствий: **adaptation/heuristic**. Перед применением маркируй связь как `direct`, `analogy` или `speculative`. Не выдавай архитектурную аналогию за каноническое содержание приёма.

Расширенный reference-файл. Для каждого приёма Альтшуллера дан конкретный software-паттерн, инструменты и триггеры применения. Используй вместе с основным SKILL.md.

---

## Приём 1: Дробление (Segmentation)

- **Суть**: Разделить объект на независимые части; сделать объект разборным; увеличить степень дробления
- **💻 Software-паттерн**: Микросервисная архитектура (разбиение монолита по доменам); шардирование БД (разделение данных по диапазонам ключей); разделение God-класса на Single-Responsibility компоненты; конфигурация по окружениям (dev/staging/prod) вместо одного гигантского конфига; split-brain разрешение в distributed systems (Raft/Paxos)
- **🔧 Инструменты**: Kubernetes (pod-ы как «отсеки»), PostgreSQL partitions, Vitess (шардирование MySQL), Consul/etcd (распределённый консенсус)
- **Когда применять в софте**: Монолит не масштабируется горизонтально; база данных упирается в размер одной машины; кодовая база стала неуправляемой; одна команда блокирует релизный цикл

## Приём 2: Вынесение (Taking out)

- **Суть**: Отделить мешающую часть или свойство от объекта; выделить только нужную функцию
- **💻 Software-паттерн**: Sidecar-паттерн (логирование/трейсинг из сервиса в sidecar-контейнер Envoy); Strangler Fig (вынесение легаси-функций в новый сервис); CQRS (выделение read-модели из write-модели); External Secrets (вынос секретов в Vault/SealedSecrets); выделение фоновых задач в отдельный worker (Sidekiq/Celery)
- **🔧 Инструменты**: Envoy/Linkerd (service mesh sidecar), HashiCorp Vault, Sidekiq, Temporal (workflow engine)
- **Когда применять в софте**: Сервис делает «слишком много»; общий код дублируется в N проектах; чувствительная логика (платежи) смешана с общей; кросскаттинг-концерны (логи, трейсинг) засоряют бизнес-логику

## Приём 3: Местное качество (Local quality)

- **Суть**: Перейти от однородной структуры к неоднородной; дать разным частям разные свойства и функции
- **💻 Software-паттерн**: Разные стратегии кэширования для разных типов данных (TTL 60s для цен, 24h для конфигов); разные isolation levels для разных транзакций (READ COMMITTED для UI, SERIALIZABLE для платежей); hot/cold/warm storage (Redis для горячих, Postgres для тёплых, S3 для холодных данных); tiered architecture (разные SLA для разных tier-ов)
- **🔧 Инструменты**: Redis + Postgres + S3 (multi-tier storage), PostgreSQL transaction isolation levels, CDN с разными TTL по URL-паттернам
- **Когда применять в софте**: Одна и та же конфигурация применяется ко всем данным без учёта их природы; все запросы обслуживаются по одному пути; кэш инвалидируется весь сразу вместо точечной инвалидации

## Приём 4: Асимметрия (Asymmetry)

- **Суть**: Перейти от симметричной формы к асимметричной; усилить полезную несимметричность
- **💻 Software-паттерн**: Primary-Replica (один мастер на запись, много реплик на чтение — асимметричная нагрузка); неравномерный шардинг (hot shard получает больше ресурсов); CAP-теорема на практике (жертвуем consistency в пользу availability для некритичных данных); разная частота деплоя для разных сервисов (core — раз в неделю, frontend — несколько раз в день)
- **🔧 Инструменты**: PostgreSQL streaming replication, Redis Cluster с хэш-слотами, Nginx с weighted upstream
- **Когда применять в софте**: Read-heavy нагрузка (100:1 reads к writes); один шард перегревается; все сервисы деплоятся с одинаковой частотой, тормозя быстрые команды

## Приём 5: Объединение (Merging)

- **Суть**: Соединить однородные объекты или операции; выполнять смежные действия совместно
- **💻 Software-паттерн**: API Gateway (аутентификация + ratelimiting + роутинг + логирование в одном месте); монорепо с shared конфигами и CI; shared library вместо копипасты; унифицированный CI/CD пайплайн; batch processing (накопить N событий и обработать одним запросом к БД); GraphQL federation (объединить данные из нескольких сервисов в один запрос)
- **🔧 Инструменты**: Kong/NGINX (API Gateway), Nx/Turborepo (monorepo), GraphQL (Apollo Federation), Redis pipelining (batch commands)
- **Когда применять в софте**: Каждый сервис повторяет одну и ту же логику (auth, logging, validation); десяток репозиториев с одинаковыми настройками CI; пользователь делает N запросов вместо одного

## Приём 6: Универсальность (Universality)

- **Суть**: Сделать объект способным выполнять несколько функций, убрать вспомогательные элементы
- **💻 Software-паттерн**: Универсальный SDK/клиент (одна библиотека для работы с API вместо трёх); multi-tenant архитектура (один инстанс обслуживает всех клиентов); plugin-архитектура с extension points; headless CMS (один бэкенд — веб, мобилка, API); Backstage (один developer portal для всей компании)
- **🔧 Инструменты**: Backstage (developer portal), Strapi/Contentful (headless CMS), plugin-архитектуры (VSCode extensions)
- **Когда применять в софте**: Три разных сервиса делают почти одно и то же; клиенты используют разные SDK с разными багами; каждый продукт городит свой developer portal

## Приём 7: Матрёшка (Nested doll)

- **Суть**: Поместить один объект внутрь другого; сделать объект проходящим сквозь полость другого
- **💻 Software-паттерн**: Docker/OCI-контейнеры (приложение внутри контейнера внутри пода); вложенные виртуализации (VM inside VM); вложенные транзакции (savepoints); рекурсивные структуры данных (JSON, AST); namespace-изоляция в Linux; nested routing (React Router внутри Layout)
- **🔧 Инструменты**: Docker, Kubernetes (Pod → Container → App), PostgreSQL savepoints, Linux cgroups/namespaces
- **Когда применять в софте**: Нужна изоляция уровней; сложная иерархия компонентов; многослойная структура данных; вложенные UI-компоненты

## Приём 8: Антивес (Anti-weight)

- **Суть**: Компенсировать вес объекта соединением с другим объектом или внешней средой
- **💻 Software-паттерн**: Load balancer для компенсации неравномерной нагрузки; backpressure в реактивных системах (замедление upstream при перегрузке downstream); rate limiting для защиты downstream-сервисов; auto-scaling для компенсации пиков; CDN offloading (разгрузка origin-сервера)
- **🔧 Инструменты**: Nginx/HAProxy (load balancing), HPA (Kubernetes), CloudFront/Cloudflare (CDN offloading), Reactive Streams (backpressure)
- **Когда применять в софте**: Один сервис перегружен, а другие простаивают; пиковая нагрузка кладёт систему; медленный downstream тормозит весь pipeline

## Приём 9: Предварительное антидействие (Preliminary anti-action)

- **Суть**: Заранее выполнить действие, компенсирующее будущий вред; подготовить систему к конфликту
- **💻 Software-паттерн**: Pre-warming кэша до деплоя (чтобы холодный старт не убил БД); circuit breaker pre-conditions (разогреть лимиты до того, как трафик пойдёт); graceful shutdown (заранее снять сервис с балансировщика, drain connections); заранее выделенные ресурсы под пик (Чёрная пятница); database index rebuild в непиковые часы
- **🔧 Инструменты**: HPA с scheduled scaling, Kubernetes preStop hooks, connection draining, Redis cache warming scripts
- **Когда применять в софте**: Холодный старт убивает БД; деплой вызывает всплеск ошибок; пиковая нагрузка предсказуема (распродажа, релиз)

## Приём 10: Предварительное действие (Preliminary action)

- **Суть**: Выполнить нужное действие заранее, чтобы сработало без задержки
- **💻 Software-паттерн**: Кэширование (Redis) до пользовательского запроса; build-time генерация статики (SSG — Next.js, Hugo); pre-warming пула соединений с БД; предзагрузка данных в CDN; кодогенерация на этапе сборки (gRPC stubs, GraphQL types); материализованные представления (pre-computed queries в Postgres)
- **🔧 Инструменты**: Redis, CDN (CloudFront), Next.js SSG, PostgreSQL materialized views, connection pooling (PgBouncer)
- **Когда применять в софте**: Первый запрос — в 10 раз медленнее повторных; данные редко меняются, но часто читаются; вычисления повторяются для каждого пользователя

## Приём 11: «Заранее подложить подушку» (Beforehand cushioning)

- **Суть**: Компенсировать низкую надёжность заранее подготовленными защитами
- **💻 Software-паттерн**: Graceful degradation (если сервис недоступен — показать кэшированные данные); fallback-стратегии в API (primary → secondary → cache → static default); retry с exponential backoff; dead letter queues (неудачные сообщения не теряются); circuit breaker (прекратить вызовы падающего сервиса, чтобы не каскадировать отказ); database replicas для failover
- **🔧 Инструменты**: Resilience4j/Polly (circuit breaker), RabbitMQ/Kafka dead letter queues, PostgreSQL streaming replication (failover), Cloudflare «Always Online»
- **Когда применять в софте**: Внешний сервис нестабилен; БД может упасть; сетевые сбои между дата-центрами; каскадные отказы в микросервисах

## Приём 12: Эквипотенциальность (Equipotentiality)

- **Суть**: Изменить условия, чтобы не приходилось преодолевать перепады
- **💻 Software-паттерн**: Service mesh (убирает разницу между локальным и удалённым вызовом); Repository-паттерн (одинаковый интерфейс для разных хранилищ); абстракция over cloud providers (Terraform — один код для AWS/GCP/Azure); унифицированный API для разных транспортов (gRPC + REST из одного proto-файла)
- **🔧 Инструменты**: Istio/Linkerd (service mesh), Terraform (multi-cloud), Repository pattern (DDD), gRPC-gateway
- **Когда применять в софте**: Локальная разработка отличается от прода; переезд между облаками — год проекта; разные протоколы для одних и тех же данных

## Приём 13: Наоборот (The other way round)

- **Суть**: Сделать процесс противоположным привычному; перевернуть объект или действие
- **💻 Software-паттерн**: Push вместо Pull (WebSocket/SSE вместо polling); инвертированные индексы (поиск по содержимому вместо перебора); event sourcing (хранить события, а не текущее состояние); Inversion of Control / Dependency Injection; Reactive Programming (данные толкают изменения в UI, а не UI опрашивает данные); «перевернуть» БД: читать из реплики, писать в мастер (а не всё в один инстанс)
- **🔧 Инструменты**: WebSocket/SSE (push), Elasticsearch (инвертированный индекс), RxJS (reactive), DI-контейнеры, EventStoreDB
- **Когда применять в софте**: Polling жрёт ресурсы вхолостую; прямой доступ создаёт coupling; синхронные цепочки вызовов блокируют поток

## Приём 14: Сфероидальность (Spheroidality)

- **Суть**: Перейти от прямых линий к криволинейным, сферическим, вращательным формам
- **💻 Software-паттерн**: Consistent hashing (минимальные перестройки при добавлении/удалении узла); round-robin с весами как «катящийся шар» по кольцу; кольцевая топология в P2P-сетях (Chord, Kademlia); кольцевые буферы (circular buffers для стриминга); Merkle trees (древовидная структура для проверки целостности)
- **🔧 Инструменты**: HAProxy consistent hashing, Discord's consistent hashing, Kafka (кольцевой лог-буфер), Cassandra (кольцевая топология)
- **Когда применять в софте**: Простое round-robin даёт массовые перестройки при добавлении узла; нужно равномерное распределение; кэш-кластер часто меняет размер

## Приём 15: Динамичность (Dynamics)

- **Суть**: Сделать объект или среду изменяемыми, подстраиваемыми под режим работы
- **💻 Software-паттерн**: Feature flags (постепенное раскатывание фич); адаптивный битрейт (HLS/DASH для видео); автоскейлинг (HPA в Kubernetes); A/B-тестирование с динамическим трафиком; graceful degradation под нагрузкой (отключение некритичных фич); динамический rate limiting (зависит от здоровья downstream); adaptive page size (маленькие страницы при высокой нагрузке)
- **🔧 Инструменты**: LaunchDarkly, HPA/VPA (Kubernetes), Nginx dynamic rate limiting, HLS/DASH
- **Когда применять в софте**: Один фиксированный режим плохо работает в разных условиях; пиковая и обычная нагрузка отличаются в 10 раз; нужно A/B-тестировать фичи без редеплоя

## Приём 16: Частичное или избыточное действие (Partial or excessive action)

- **Суть**: Если трудно получить ровно 100% эффекта, получить немного меньше или немного больше
- **💻 Software-паттерн**: Приближённые вычисления (HyperLogLog для count distinct, Top-K для частых элементов); Bloom filter (быстрая проверка «возможно есть» вместо точной «есть/нет»); сэмплирование трейсов (1% вместо 100% сбора); pagination вместо полной загрузки; Lazy loading (избыточно загрузить чуть больше данных, чем нужно на экран, чтобы избежать второго запроса)
- **🔧 Инструменты**: Redis HyperLogLog, Bloom filters, OpenTelemetry sampling, GraphQL Relay pagination
- **Когда применять в софте**: Точный подсчёт слишком дорог; 100% данных не нужны для принятия решения; полная загрузка убивает latency

## Приём 17: Переход в другое измерение (Another dimension)

- **Суть**: Использовать вертикаль, многоуровневость, объём вместо плоскости
- **💻 Software-паттерн**: Многоуровневый кэш (L1 in-memory → L2 Redis → L3 Postgres → L4 S3); multi-tier архитектура (CDN → API Gateway → BFF → микросервисы → БД); 3D-визуализация данных вместо плоских таблиц; многослойная защита (WAF → API Gateway → Network Policies → App auth); вертикальное масштабирование (более мощный инстанс вместо десятка мелких)
- **🔧 Инструменты**: Multi-level caching (Caffeine → Redis → DB), AWS WAF + Security Groups, Grafana 3D-панели, K8s multi-tier
- **Когда применять в софте**: Плоская архитектура не справляется с разными требованиями; один кэш-слой даёт либо hit rate 60%, либо дорого; безопасность «в один слой» легко обходится

## Приём 18: Механическая вибрация (Mechanical vibration)

- **Суть**: Привести объект в колебание; использовать резонанс
- **💻 Software-паттерн**: Heartbeat/health check (регулярная «вибрация» для проверки живости); keep-alive пакеты в TCP; fuzzing (подача случайных/искажённых данных для поиска уязвимостей); chaos engineering (намеренная «вибрация» системы для проверки устойчивости); cache warming через периодические запросы
- **🔧 Инструменты**: Kubernetes liveness probes, Chaos Monkey (Netflix), AFL/libFuzzer, wrk/k6 (load testing)
- **Когда применять в софте**: Сервис умирает молча без алерта; система не тестировалась на странных входных данных; поведение под нагрузкой неизвестно

## Приём 19: Периодическое действие (Periodic action)

- **Суть**: Перейти от непрерывного действия к импульсному или циклическому
- **💻 Software-паттерн**: Cron-джобы (периодическая очистка, агрегация, синхронизация); batch processing вместо real-time (собрать 1000 событий → обработать пачкой); polling с интервалом (проверять статус задачи каждые N секунд); TTL-based cache refresh (периодическое обновление вместо инвалидации по событию); periodic reconciliation loop (Kubernetes controller pattern)
- **🔧 Инструменты**: Kubernetes CronJob, Sidekiq scheduled jobs, Airflow (batch pipelines), Redis TTL
- **Когда применять в софте**: Непрерывный polling жрёт CPU; real-time не нужен — достаточно near-real-time; проще запускать раз в час, чем поддерживать постоянное соединение

## Приём 20: Непрерывность полезного действия (Continuity of useful action)

- **Суть**: Вести полезную работу непрерывно; убрать паузы и простои
- **💻 Software-паттерн**: Streaming вместо batch (Kafka/Spark Streaming — непрерывный поток); connection pooling (держать соединения открытыми вместо пересоздания); hot reload / zero-downtime deploy (blue-green, rolling update); keep-alive соединения HTTP/2; continuous deployment (каждый коммит → прод без пауз)
- **🔧 Инструменты**: Kafka/Flink (streaming), PgBouncer (connection pool), Kubernetes rolling update, HTTP/2 multiplexing
- **Когда применять в софте**: Соединения пересоздаются на каждый запрос; деплой вызывает простой; batch-окно создаёт задержку в N часов

## Приём 21: Проскок (Skipping)

- **Суть**: Быстро пройти вредную или опасную стадию
- **💻 Software-паттерн**: Fail fast (быстро вернуть ошибку вместо retry storm); optimistic locking (быстро попробовать, при конфликте откатить, вместо долгого ожидания блокировки); skip list (структура данных для быстрого поиска с вероятностным балансом); TCP Fast Open (пропустить handshake для повторных соединений); quick check перед дорогой операцией (validate input → если невалидно, не ходить в БД)
- **🔧 Инструменты**: Optimistic locking (JPA @Version), skip list (Redis sorted sets), TCP Fast Open, input validation middleware
- **Когда применять в софте**: Дорогая операция выполняется даже для заведомо невалидных данных; retry storm каскадирует отказ; pessimistic locking создаёт очереди

## Приём 22: «Обратить вред в пользу» (Blessing in disguise)

- **Суть**: Использовать вредный фактор как полезный ресурс
- **💻 Software-паттерн**: Тепло ошибок → ML-модель предсказания инцидентов (логи ошибок → обучение предиктивной модели); Chaos Engineering (превратить случайные отказы в инструмент тестирования); трафик ботов → нагрузочное тестирование; спам → training data для spam-фильтра; холодный старт сервера → повод прогреть кэш
- **🔧 Инструменты**: Chaos Monkey, ELK stack для ML на логах, reCAPTCHA (боты → training data)
- **Когда применять в софте**: Ошибки просто логируются и забываются; боты только блокируются, не анализируются; отказы воспринимаются как чистая проблема

## Приём 23: Обратная связь (Feedback)

- **Суть**: Ввести контроль по результату; усилить или изменить характер обратной связи
- **💻 Software-паттерн**: Мониторинг (Prometheus/Grafana с алертами по SLO); HPA (горизонтальное автоскейлирование по CPU/memory/latency); автоматический откат деплоя при росте ошибок; Canary deployment с анализом метрик (медленно наращиваем трафик, смотрим на метрики); circuit breaker (обратная связь о здоровье downstream); A/B-тестирование с автоматическим выбором победителя
- **🔧 Инструменты**: Prometheus + Grafana + Alertmanager, Argo Rollouts (canary), HPA, Resilience4j circuit breaker
- **Когда применять в софте**: Нет видимости, что система делает в проде; скейлинг реактивный (после того как уже упало); деплой катится без контроля метрик

## Приём 24: Посредник (Intermediary)

- **Суть**: Использовать промежуточный объект для передачи действия
- **💻 Software-паттерн**: API Gateway (посредник между клиентом и микросервисами); Message Broker (Kafka/RabbitMQ как посредник между producer и consumer); Service Mesh (Envoy как посредник для всего трафика); OAuth/OIDC-провайдер (посредник аутентификации); Proxy (кэширующий, reverse, forward); DNS как посредник Service Discovery
- **🔧 Инструменты**: Kong/Envoy, Kafka, Istio, OAuth2/OIDC, Nginx, Consul DNS
- **Когда применять в софте**: Прямые вызовы создают coupling; сервисы должны знать адреса друг друга; аутентификация размазана по всем сервисам

## Приём 25: Самообслуживание (Self-service)

- **Суть**: Сделать объект самообслуживающимся; использовать собственные ресурсы
- **💻 Software-паттерн**: Self-healing (liveness probe → автоматический restart пода); auto-scaling (самостоятельное масштабирование); self-service developer portal (Backstage); саморегистрирующиеся сервисы (Consul service discovery); автоматическая ротация сертификатов (cert-manager); vacuum/cleanup процессов (autovacuum в Postgres)
- **🔧 Инструменты**: Kubernetes (self-healing), Backstage, cert-manager, Consul, PostgreSQL autovacuum
- **Когда применять в софте**: Ops-команда — бутылочное горлышко; сервисы требуют ручного восстановления после падения; разработчики ждут доступы

## Приём 26: Копирование (Copying)

- **Суть**: Использовать упрощённые, дешёвые или виртуальные копии вместо оригинала
- **💻 Software-паттерн**: CDN (географические копии статики); read-реплики БД (копии для чтения); Redis как кэш-копия горячих данных; stub/mock-сервисы для локальной разработки; LQIP (Low Quality Image Placeholders — размытая копия до загрузки полного изображения); snapshot-тестирование (копия вывода); shadow traffic (копия продакшен-трафика на тестовый кластер)
- **🔧 Инструменты**: CloudFront/Fastly, PostgreSQL read replicas, Redis, Jest snapshots, Traffic shadowing (Istio)
- **Когда применять в софте**: Оригинал (продакшен-БД) не тянет read-нагрузку; разработчикам нужен продакшен-образец данных; пользователи ждут загрузки больших файлов

## Приём 27: Дешёвая недолговечность взамен дорогой долговечности (Cheap short-living objects)

- **Суть**: Заменить дорогой долговечный объект набором дешёвых сменяемых
- **💻 Software-паттерн**: Ephemeral containers/окружения (одноразовые стейджинги на PR); Serverless функции (Lambda — живут секунды, не надо управлять); короткоживущие JWT-токены; immutable infrastructure (не чинить сервер — убить и пересоздать); TTL-based всё (кэш, сессии, DNS)
- **🔧 Инструменты**: AWS Lambda, Docker ephemeral containers, JWT с коротким expiry, Terraform (immutable infra)
- **Когда применять в софте**: Сервер живёт годами и превращается в snowflake; долгоживущие сессии создают проблемы безопасности; окружения для тестов копятся и не чистятся

## Приём 28: Замена механической схемы (Mechanics substitution)

- **Суть**: Заменить механическое действие на электрическое, оптическое, магнитное, программное
- **💻 Software-паттерн**: Event-driven вместо polling (Kafka/RabbitMQ вместо cron); WebSocket/SSE вместо периодических HTTP-запросов; асинхронная очередь вместо синхронной цепочки вызовов; специализированная БД вместо реляционной (Elasticsearch для поиска, TimescaleDB для метрик, Neo4j для графов); GraphQL вместо REST для гибких запросов; serverless вместо управления серверами
- **🔧 Инструменты**: Kafka, WebSocket/SSE, Elasticsearch, GraphQL, AWS Lambda, Temporal
- **Когда применять в софте**: Polling ест ресурсы 99% времени вхолостую; REST over-fetching/under-fetching; реляционная БД плохо справляется с конкретным типом нагрузки

## Приём 29: Пневматика и гидравлика (Pneumatics and hydraulics)

- **Суть**: Использовать газообразные и жидкие элементы вместо твёрдых
- **💻 Software-паттерн**: Потоковая обработка данных (Kafka Streams — «поток» данных через систему); backpressure в реактивных системах (замедление «потока» при перегрузке); ETL-пайплайны (данные «текут» через стадии трансформации); буферы/очереди как «гидроаккумуляторы» (сглаживание пиков); leaky bucket алгоритм для rate limiting
- **🔧 Инструменты**: Kafka Streams, Reactive Streams (Project Reactor/RxJava), Airflow (ETL), leaky bucket rate limiter
- **Когда применять в софте**: Batch-обработка создаёт задержки; пиковая нагрузка ломает систему без буфера; жёсткий rate limiting отбрасывает запросы вместо сглаживания

## Приём 30: Гибкие оболочки и тонкие плёнки (Flexible shells and thin films)

- **Суть**: Использовать гибкие оболочки, мембраны, плёнки для изоляции
- **💻 Software-паттерн**: API Facade/Thin Wrapper (тонкий слой над легаси для совместимости); Docker-образы (тонкий слой над приложением); Network Policies (тонкий слой сетевой изоляции между подами); Decorator-паттерн (обернуть поведение, не меняя ядро); Service Mesh sidecar (тонкий прокси-слой для всего трафика); адаптер между incompatible интерфейсами
- **🔧 Инструменты**: Docker, Kubernetes Network Policies, Decorator pattern, Envoy sidecar, Adapter pattern
- **Когда применять в софте**: Легаси-система с неудобным API; нужна изоляция без тяжёлой VM; кросскаттинг-концерны размазаны по коду

## Приём 31: Применение пористых материалов (Porous materials)

- **Суть**: Сделать объект пористым; использовать капилляры и микропоры
- **💻 Software-паттерн**: Bloom filter («пористый» фильтр — пропускает только вероятные совпадения); rate limiter с leaky bucket («протекающее ведро» — медленно пропускает запросы); sparse data structures (разрежённые матрицы — храним только ненулевые значения); фильтрация на уровне БД (WHERE в SQL — «пора» для нужных строк); coarse-grained проверка перед fine-grained (быстрый фильтр → точная проверка)
- **🔧 Инструменты**: Redis Bloom filters, leaky bucket алгоритмы, sparse matrices (SciPy), SQL WHERE clauses, CQRS query-side optimisation
- **Когда применять в софте**: 99% данных отфильтровываются, но проверка каждого элемента дорога; нужен предварительный грубый фильтр; полная структура данных не влезает в память

## Приём 32: Изменение окраски (Color changes)

- **Суть**: Изменить цвет, прозрачность, отражающую способность для наблюдаемости
- **💻 Software-паттерн**: Observability (делаем невидимое видимым: логи, метрики, трейсы); цветовое кодирование алертов по severity (красный/жёлтый/зелёный); feature flags как «окраска» UI; подсветка синтаксиса в IDE; heatmaps на дашбордах; статус-индикаторы (зелёный — ОК, красный — down); разная «окраска» окружений (синий = staging, зелёный = production в blue-green деплое)
- **🔧 Инструменты**: Grafana (heatmaps, статус-панели), Datadog APM, LaunchDarkly, IDE syntax highlighting
- **Когда применять в софте**: Не видно, что система делает; алерты приходят, но не ясен масштаб; статус сервисов непонятен без захода в консоль

## Приём 33: Однородность (Homogeneity)

- **Суть**: Делать взаимодействующие объекты из одинаковых или совместимых материалов
- **💻 Software-паттерн**: Стандартизация (один язык/фреймворк во всей команде); единый формат логов (структурированный JSON); Protocol Buffers для унификации схем данных; монорепо с общими стандартами (ESLint, Prettier, tsconfig); единый CI/CD для всех сервисов; унифицированные SDK для разных языков
- **🔧 Инструменты**: ESLint/Prettier (единый стиль), Protobuf (единый формат), Turborepo/Nx (единый билд), monorepo
- **Когда применять в софте**: Каждый сервис логирует в своём формате; команды используют разные языки без необходимости; API-контракты расходятся между сервисами

## Приём 34: Отброс и регенерация частей (Discarding and recovering)

- **Суть**: Отбросить отработавшую часть; восстанавливать изношенные части в процессе
- **💻 Software-паттерн**: Garbage Collection (автоматический отброс ненужных объектов); TTL-based cache eviction (автоматический отброс протухших данных); пересоздание подов в Kubernetes (убить и пересоздать вместо починки); rebuild вместо repair (CI/CD билдит с нуля); connection pool с пересозданием протухших соединений; log rotation (отброс старых логов, начало новых)
- **🔧 Инструменты**: JVM GC, Redis TTL eviction, Kubernetes pod lifecycle, logrotate, PgBouncer connection recycling
- **Когда применять в софте**: Данные копятся бесконечно; поды живут месяцами и деградируют; пул соединений полон мёртвых коннектов

## Приём 35: Изменение агрегатного состояния (Parameter changes / state change)

- **Суть**: Изменить агрегатное состояние, плотность, гибкость, температуру
- **💻 Software-паттерн**: Сериализация/десериализация (объект → JSON → объект); сжатие данных (уменьшение «объёма»); Lazy loading (данные «заморожены» до востребования — не загружены в память); marshalling/unmarshalling; cold storage (сжатые/архивированные данные) vs hot storage (распакованные, готовые к использованию); индексация (изменение «состояния» данных для быстрого поиска)
- **🔧 Инструменты**: JSON/Protobuf (сериализация), gzip/brotli (сжатие), ORM lazy loading, S3 Glacier (cold storage), Elasticsearch indexing
- **Когда применять в софте**: Данные передаются в неоптимальном формате; хранение неиспользуемых полей жрёт память; полная загрузка объекта ради одного поля

## Приём 36: Фазовые переходы (Phase transitions)

- **Суть**: Использовать эффекты при плавлении, кипении, конденсации
- **💻 Software-паттерн**: Холодный/горячий старт приложения (переход из «замороженного» состояния в «рабочее»); промоушн staging → production (переход между «фазами» жизненного цикла); L1/L2/L3 кэш с разной «температурой» данных (горячие → in-memory, тёплые → Redis, холодные → S3); grace period в rate limiting (переход от relaxed к strict режиму); JIT-компиляция (переход из байт-кода в машинный код при «нагреве»)
- **🔧 Инструменты**: Multi-level caching (Caffeine → Redis → S3), JVM JIT compiler, ArgoCD promotion, rate limiter grace period
- **Когда применять в софте**: Холодный старт приложения медленный; данные используются с разной частотой; жёсткое переключение режимов ломает пользователей

## Приём 37: Тепловое расширение (Thermal expansion)

- **Суть**: Использовать тепловое расширение или сжатие материалов
- **💻 Software-паттерн**: Автоскейлинг по метрикам (расширение под нагрузкой, сжатие при спаде); динамический массив (ArrayList — расширение при заполнении); buffer growth (увеличение буфера при переполнении); elasticsearch scaling (автоматическое добавление/удаление нод); dynamic thread pool (расширение пула при росте очереди)
- **🔧 Инструменты**: Kubernetes HPA/VPA, ArrayList/Vector (dynamic arrays), Elasticsearch cluster scaling, ThreadPoolExecutor с dynamic sizing
- **Когда применять в софте**: Система не адаптируется к пикам; буфер переполняется вместо роста; фиксированный пул потоков не справляется

## Приём 38: Применение сильных окислителей (Strong oxidants)

- **Суть**: Заменить обычную среду обогащённой кислородом или сильным окислителем
- **💻 Software-паттерн**: Прямой software-аналог отсутствует. Косвенно: агрессивная инвалидация кэша (полная очистка вместо точечной); полная переиндексация БД (REINDEX вместо частичной); drop and recreate вместо миграции; пересборка с нуля вместо инкрементальной; hard reset вместо soft reset
- **🔧 Инструменты**: Redis FLUSHALL, PostgreSQL REINDEX, Terraform destroy + apply, Docker rebuild --no-cache
- **Когда применять в софте**: Инкрементальные изменения накопили ошибки; проще сжечь и построить заново, чем чинить; кэш деградировал до бесполезного состояния

## Приём 39: Применение инертной среды (Inert atmosphere)

- **Суть**: Заменить обычную среду инертной; вести процесс в вакууме или защитной атмосфере
- **💻 Software-паттерн**: Sandbox-изоляция (запуск непроверенного кода в изолированной среде); контейнеризация (Docker — «инертная» среда для приложения); виртуальные окружения (Python venv, Nix shell); read-only файловые системы; network isolation (закрыть все порты кроме нужных); gVisor/Firecracker (microVM изоляция)
- **🔧 Инструменты**: Docker, gVisor, Firecracker, Python venv, K8s NetworkPolicies, seccomp/AppArmor
- **Когда применять в софте**: Код из непроверенных источников; приложение конфликтует с окружением; безопасность требует изоляции

## Приём 40: Композиционные материалы (Composite materials)

- **Суть**: Перейти от однородного материала к композиционному
- **💻 Software-паттерн**: Микросервисная архитектура (комбинация специализированных сервисов); Polyglot persistence (разные БД под разные задачи — Postgres для транзакций, Elasticsearch для поиска, Redis для кэша); Multi-cloud strategy (разные облака для разных задач); комбинация синхронных и асинхронных вызовов; гибридное хранение (structured + unstructured); multi-paradigm programming (OOP + FP + reactive)
- **🔧 Инструменты**: Postgres + Elasticsearch + Redis + S3, Terraform multi-cloud, Apache Kafka + gRPC, multi-paradigm languages (Scala, Kotlin, Rust)
- **Когда применять в софте**: Одна БД не справляется со всеми типами запросов; одно облако — single point of failure; один стиль программирования не подходит для всех компонентов
