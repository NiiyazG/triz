# TRIZ 3.0 — гибридный решатель изобретательских и противоречивых задач

## Назначение

Преобразуй исходную проблему в проверяемое решение, устраняющее корневое противоречие с минимальным усложнением системы. Ядро — ТРИЗ; смежные методики подключаются, когда природа задачи вне чистого противоречия (дилемма, нехватка знания, сеть проблем, перебор конфигураций, выбор концепции). Не подменяй ТРИЗ мозговым штурмом, не называй упрощённый маршрут АРИЗ и не применяй детерминированный анализ противоречий к complex/chaotic задачам.

## When to Use

Загружай навык, когда:

- улучшение `A` ухудшает `B` (техническое противоречие);
- элемент должен обладать взаимоисключающими свойствами (физическое противоречие);
- обычная оптимизация даёт только компромисс;
- нужна дилемма без приемлемого компромисса (ценностная/политическая);
- несколько взаимосвязанных противоречий, нужна «большая картина»;
- не хватает знания, чтобы сформулировать противоречие;
- нужно систематически перебрать конфигурации или выбрать концепцию;
- пользователь просит ТРИЗ, ИКР, противоречие, функциональный анализ, веполь, 40 приёмов, тримминг, FOS, TESE, АРИЗ или конкретную смежную методику.

Не активируй для обычного исправления кода, перевода, вычисления, краткого списка идей или задачи без конфликта, пока метод не добавляет ценности.

## Основные правила

1. Сначала найди правильную задачу, затем решай её.
2. Сначала определи природу задачи (см. «Смыслообразование»), затем выбери метод.
3. Отделяй факт, допущение, гипотезу и рекомендацию.
4. Не выдумывай противоречие, патент, научный эффект, метрику или источник.
5. Авторские software-соответствия называй эвристиками, а не канонической матрицей Альтшуллера.
6. АРИЗ-85С применяй только к сложной ключевой мини-задаче, не решённой более простыми инструментами.
7. Предлагай несколько концепций, затем независимо проверяй их.
8. Решение считается сильным, если полезный параметр улучшен без недопустимого ухудшения связанного параметра и без более тяжёлого нового конфликта.

## Смыслообразование и честные выходы

### Домен задачи (Cynefin)

| Домен | Признак | Действие |
|---|---|---|
| Clear | известный алгоритм, устойчивая причинность | применяй стандарт, не изобретай |
| Complicated | есть экспертиза, причинность устанавливается анализом | анализ → метод → решение |
| Complex | причинность видна только ретроспективно, эмерджентность | probe–sense–respond: OTSM/C-K/эксперименты, не детерминированный анализ |
| Chaotic | нет стабильности, срочность | сначала стабилизируй, затем перейди к Complicated |

См. `references/cynefin-routing.md`.

### Честные выходы маршрутизатора

Честный выход — **стоп-правило**, а не отдельный обязательный шаг. Применяй, когда противоречие не формулируется без выдумки:

- «обычная оптимизация» — противоречия нет, применяй стандартную инженерию;
- «сначала измерить» — данных недостаточно для ТП/ФП (не выдумывай противоречие);
- «данных недостаточно» — сформулируй допущения и покажи, какие данные изменят вывод;
- «при заданных ограничениях решения не найдено» — это не доказательство невозможности;
- «физический предел» — если закон (термодинамика, пропускная способность, сложность) не позволяет: вернись к постановке (снизь требование / измени систему), не выдавай «решение», не покрывающее предел.

## Triage и маршрутизация

### Природа задачи (диагностика)

| Наблюдение | Природа | Основной метод |
|---|---|---|
| Улучшение `A` ухудшает `B` | техническое противоречие | изобретательские принципы, матрица как подсказка |
| Свойство требуется и не требуется по условиям | физическое противоречие | разделение + эффекты/FOS |
| Две ценности конфликтуют, компромисс неприемлем | ложная дилемма | TOC Evaporating Cloud (вскрытие допущений) |
| Множество связанных недостатков/противоречий | сеть проблем | OTSM Network of Problems |
| Не хватает знания для формулировки противоречия | неопределённость | C-K theory / «сначала измерить» |
| Ограничения несовместимы | невыполнимость | зафиксируй противоречие в ограничениях, вернись к постановке |
| Несколько концепций, несколько критериев | многокритериальный выбор | Decision Analysis (NASA/Pugh) |

Явно назови доминирующий подтип; если природа смешанная (ТП + скрытая дилемма), реши оба. Отдельно проверь пути «вне противоречия» — улучшения, которые вообще не конфликтуют (данные, калибровка, порядок операций): их нельзя упускать, увлёкшись формулировкой противоречия. Для чистого выбора между готовыми концепциями не формулируй ИКР — сразу используй `references/decision-analysis.md`.

### Уровень задачи

| Уровень | Признаки | Маршрут |
|---|---|---|
| Быстрый | одна ясная пара параметров, известны ограничения | ТП → ИКР → ресурсы → 2–4 модели решения → проверка |
| Стандартный | симптом неоднозначен, несколько функций/компонентов | границы → функциональный анализ/CECA → ключевая задача → ТП/ФП → маршрутизатор |
| Глубокий | системный конфликт, решения ухудшают систему, высокая цена ошибки | полный анализ → ключевая мини-задача → ARIZ-85C → обоснование концепции |

Если данных не хватает, не останавливай анализ: сформулируй минимальные допущения, отметь их и покажи, какие данные сильнее всего изменят вывод.

## Procedure

### 1. Зафиксировать исходную нежелательную ситуацию

Опиши наблюдаемый вред, цель, ограничения, стейкхолдеров и цену бездействия. Сформулируй административное противоречие: «нужно получить X, но неизвестно как сделать это при ограничениях Y».

### 2. Определить границы и временной масштаб

Укажи систему, подсистемы, надсистему, целевой объект, основную функцию и рассматриваемые прошлое/настоящее/будущее. Для сложных задач загрузи `references/problem-identification.md`.

### 3. Найти ключевую задачу

Для стандартного/глубокого трека выполни минимально достаточный набор:

- компонентный и функциональный анализ;
- анализ потоков вещества, энергии или информации;
- причинно-следственную цепочку недостатков (CECA);
- выбор ключевого недостатка, который реально можно изменить.

### 4. Сформулировать противоречия

- **ТП:** если улучшить `[A]`, ухудшается `[B]`.
- **ФП:** `[элемент/зона]` должен быть `[свойство]` при условии `[C1]` и не быть `[свойство]` при `[C2]`.

Проверь обе стороны ТП: изменение в прямом и обратном направлениях. Для ФП загрузи `references/physical-contradictions.md`.

### 5. Сформулировать ИКР и идеальность

ИКР: целевой объект/система сама устраняет вред и сохраняет полезную функцию без введения сложного нового элемента и недопустимых затрат.

Оцени направление идеальности качественно:

`полезные эффекты / (затраты + вред + сложность + риски)`.

Не выдавай эту запись за универсальную точную формулу.

### 6. Инвентаризировать ресурсы

Проверь доступные вещества/компоненты, поля/энергию, пространство, время, информацию, функции, структуру, среду и надсистему. Сначала используй бесплатные или уже присутствующие ресурсы. См. `references/resources.md`.

### 7. Выбрать инструмент по модели проблемы

| Модель проблемы | Основной инструмент |
|---|---|
| Техническое противоречие | противоречие + изобретательские принципы; матрица только как подсказка |
| Физическое противоречие | разделение во времени/пространстве/по условию/между уровнями + эффекты/FOS |
| Ложная дилемма без компромисса | TOC Evaporating Cloud — вскрытие допущений за логическими связями |
| Сеть взаимосвязанных противоречий | OTSM Network of Problems — «большая картина» и bottleneck |
| Нехватка знания | C-K theory — расширение концептов из доступного знания |
| Перебор конфигураций | морфологический анализ + cross-consistency assessment |
| Связанные требования | Axiomatic Design — детекция coupled функциональных требований |
| Неполное, недостаточное или вредное взаимодействие | Su-Field + маршрутизация к 76 стандартным решениям |
| Дорогой/избыточный компонент | тримминг и перенос функции |
| Нужно новое средство реализации функции | функционально-ориентированный поиск, база эффектов, биомимикрия |
| Генерация идей в границах системы | SIT (closed world), синектика, латеральное мышление |
| Выбор между концепциями | Decision Analysis — критерии с операциональными определениями |
| Нужен прогноз развития | S-кривая и TESE |
| Осталась сложная ключевая мини-задача | ARIZ-85C (полный алгоритм) |

Загружай только нужный справочник из `references/`.

### 8. Сгенерировать 3–5 концепций

Для каждой концепции укажи:

- применённый инструмент;
- механизм устранения противоречия;
- какие ресурсы используются;
- предпосылки и ограничения;
- ожидаемый эффект;
- новый возможный конфликт;
- самый дешёвый тест.

Software-аналогии из `references/software-techniques.md` маркируй как `direct`, `analogy` или `speculative`.

### 9. Обосновать и отсеять

Проверь физическую/техническую реализуемость, безопасность, стоимость, масштабируемость, обратимость, сроки, доказательства и соответствие ограничениям. При необходимости используй доменного эксперта, поиск источников или эксперимент. Для выбора между концепциями загрузи `references/decision-analysis.md`. Не смешивай генерацию концепции с её независимой проверкой.

### 10. Диверсионная проверка

Спроси: «Как новое решение может вызвать отказ, вред, неправильную активацию, деградацию или скрытую зависимость?» Добавь защиту или критерий остановки.

### 11. План проверки

Определи baseline, метрики обеих сторон противоречия, guardrail-метрики, тест, критерий успеха и отката. Не используй универсальные численные пороги без контекста проекта. Для плана эксперимента загрузи `references/doe.md`.

## Формат результата

```markdown
## 1. Исходная нежелательная ситуация и допущения
## 2. Границы системы и главная функция
## 3. Домен (Cynefin) и природа задачи
## 4. Ключевая задача и причинная цепочка
## 5. Противоречия (административное, техническое, физическое — или не применимо)
## 6. ИКР и ресурсы
## 7. Выбранные инструменты
## 8. Концепции решения
## 9. Сравнение и рекомендуемая концепция
## 10. Риски и диверсионная проверка
## 11. Эксперимент, метрики и следующий шаг
## 12. Реестр доказательств и неопределённости
```

Для быстрой задачи допустим сокращённый ответ, но обязательны противоречие, ИКР, механизм решения и проверка.

## Pitfalls

- Решать первый симптом без поиска ключевого недостатка.
- Перебирать все 40 приёмов без маршрутизации.
- Считать компромисс снятием противоречия.
- Называть пятишаговую памятку АРИЗ.
- Представлять поле в Su-Field как результат взаимодействия: поле является носителем/средством взаимодействия.
- Применять механическую метафору к software без объяснения механизма.
- Применять детерминированный анализ противоречий к complex/chaotic задаче.
- Принимать ценностную дилемму за техническое противоречие.
- Переносить вред в надсистему/на другого участника/на поздний период и выдавать это за решение.
- Полагать, что попарная совместимость CCA гарантирует совместимость всей конфигурации.
- Подменять доказательство уверенным текстом.
- Делать ТРИЗ-анализ обязательным для простой рутинной задачи.

## Verification

Перед завершением проверь:

- [ ] ключевая задача отличается от симптома или обоснованно совпадает с ним;
- [ ] определён домен (Cynefin) и природа задачи, выбранный метод им соответствует;
- [ ] обе стороны ТП измеримы или наблюдаемы;
- [ ] ФП содержит условия, а не просто риторическое «и да, и нет»;
- [ ] есть минимум две независимые концепции для нетривиальной задачи;
- [ ] указаны допущения, доказательства и неопределённость;
- [ ] решение не создаёт более тяжёлого противоречия и не переносит вред скрыто;
- [ ] для сложной мини-задачи есть полный ARIZ-85C или обоснованный отказ от него;
- [ ] определены тест, метрики успеха и откат.
